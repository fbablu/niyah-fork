## 1 — otpThrottle SecureStore key (`src/utils/otpThrottle.ts`)

`keyFor` used `phone.replace(/[^+0-9]/g, "")`, which **kept the leading `+`** of an E.164 number.
`expo-secure-store` keys must match `/^[A-Za-z0-9._-]+$/` → every read/write threw and the throttle
silently never persisted. Changed to `replace(/[^0-9]/g, "")` (digits only) — still normalises
differently-formatted spellings of the same number to one record. No old records to migrate (the bad
key never wrote successfully). Tests green.

## 2 — feature-flags permission-denied (`firebase/firestore.rules`)

`useFeatureFlagsStore.subscribe()` attaches the `config/featureFlags` `onSnapshot` at app boot —
**before** Firebase Auth resolves. A Firestore listener that hits `permission-denied` is torn down
**permanently** (the store guards `if (_unsub) return`, so it never re-subscribes), which left flags
stuck on defaults for the whole session even after auth. The doc comment already said "Public
read-only", so the fix is `allow read: if true` (these are non-sensitive UX kill switches — no PII,
no money, no secrets; write stays `if false`). **Inert until `firebase deploy --only firestore:rules`.**

## 4 — Phone auth reCAPTCHA error (the deep one)

**Symptom:** on the physical dev device, phone sign-in throws
`[auth/unknown] The reCAPTCHA SDK is not linked to your app`.

**Root cause:** Firebase iOS phone auth uses **silent APNs push** for app verification, falling back
to **reCAPTCHA** when that push can't be delivered. APNs `.p8` keys *are* uploaded to Firebase (Dev
`M2F5339KYF` + Prod `BM42K87CP9`, team `4R55F73KCP`) and FCM tokens register fine — but the local
`pnpm build:local` is a **development-signed Debug build** whose `aps-environment` entitlement had
defaulted to **`production`**. A dev-signed build can only receive pushes on the **sandbox** gateway,
so Firebase Auth's silent push never landed → reCAPTCHA fallback → the (unlinked) `RecaptchaEnterprise`
SDK error. Only `RecaptchaInterop` is in the Podfile.lock; the Enterprise SDK is intentionally not
linked (the code author flagged the reCAPTCHA web flow as "brittle" and chose APNs + a disable flag).

**Fix:** `app.config.js:75` already had the lever —
`"aps-environment": process.env.EXPO_PUBLIC_APNS_ENV === "development" ? "development" : "production"`.
Set `EXPO_PUBLIC_APNS_ENV=development` in `.env` (documented in `.env.example`) and regenerate native
so the entitlement bakes in as `development` → dev build registers a **sandbox** APNs token → matches
the uploaded Development key → silent push lands → no reCAPTCHA.

**Dev vs prod (important — does NOT leak):**
- `pnpm build:local` = Debug, development-signed → sandbox → `aps-environment=development`. ✅ correct for the test phone.
- `eas build --profile production` = distribution-signed → production. EAS does **not** read the gitignored local `.env`, and its prebuild leaves `EXPO_PUBLIC_APNS_ENV` unset → defaults to `production`. ✅ App Store build is unaffected.

**Verify the entitlement after prebuild** (the shell `echo $EXPO_PUBLIC_APNS_ENV` is always blank —
Expo loads `.env` into the build process, not your shell):
```bash
grep -A1 aps-environment ios/Niyah/Niyah.entitlements   # dev build → <string>development</string>
```

**Contingency if reCAPTCHA persists after the sandbox rebuild:** Firebase **reCAPTCHA Enterprise**
enforcement (Authentication → Settings) can stick "on" and demand the SDK regardless of APNs
(firebase-ios-sdk#15345). Set it to not-enforced, or link the `RecaptchaEnterprise` pod by adding it
to `MODULAR_HEADER_PODS` in `plugins/withFirebaseStaticFrameworks.js`.

## 5 — Fresh install shows old account (expected)

iOS Keychain persists Firebase Auth credentials across app **uninstall/reinstall**; the Terms-accept
flag lives in Firestore on the user profile. So a "fresh build" auto-restores the last account and
skips Terms. This is correct iOS behavior and good for real returning users — sign out to start clean.
For the real-$ payout re-test use a **fresh non-demo account (NOT `cMtHvQ…`)** per the submit chain.

## Update — second pass (after the first rebuild still erred)

The sandbox-APNs rebuild **did not** clear the phone-auth error, and the otpThrottle warning persisted.
Root causes were deeper than the first pass:

- **otpThrottle (incomplete first fix):** the key *prefix* `@niyah/otp_throttle:` itself contains
  illegal SecureStore chars (`@`, `/`, `:`) — so the key was invalid regardless of the phone digits.
  Stripping the `+` wasn't enough. Fixed the prefix → `niyah_otp_throttle_`. The jest mock didn't
  enforce the key charset (so the green test was a false pass) — added a charset guard to the mock so
  the existing normalisation test now fails on any illegal key. (`src/utils/otpThrottle.ts` + test.)
- **Phone auth = reCAPTCHA Enterprise SDK, not just APNs.** In this FirebaseAuth version (RNFB 23.8.8),
  when silent push can't complete the iOS app-verification, the fallback is **reCAPTCHA Enterprise**,
  which requires the `RecaptchaEnterprise` pod to be **linked** — Podfile.lock only had `RecaptchaInterop`
  (the shim). The `development` entitlement is still correct/necessary, but insufficient on its own.
  Fixed by adding `pod 'RecaptchaEnterprise'` in `plugins/withFirebaseStaticFrameworks.js`. This keeps
  phone auth fully working (silent push when it succeeds, reCAPTCHA Enterprise when it can't) —
  nothing is disabled. Needs a `prebuild --clean` + rebuild (Podfile change).
- **`logEvent failed: app_open [permission-denied]`** — separate, benign: analytics `addDoc` fires
  pre-auth and is fire-and-forget `.catch`-swallowed. Not money-path, not introduced here. Address
  later (gate analytics writes behind auth, or a scoped rule) if the log noise matters.
