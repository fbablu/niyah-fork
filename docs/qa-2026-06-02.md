## 1 — otpThrottle SecureStore key (`src/utils/otpThrottle.ts`)

`keyFor` used `phone.replace(/[^+0-9]/g, "")`, which **kept the leading `+`** of an E.164 number.
`expo-secure-store` keys must match `/^[A-Za-z0-9._-]+$/` → every read/write threw and the throttle
silently never persisted. Changed to `replace(/[^0-9]/g, "")` (digits only) — still normalises
differently-formatted spellings of the same number to one record. No old records to migrate (the bad
key never wrote successfully). Tests green.

## 2 — feature-flags permission-denied (`firebase/firestore.rules`)

`useFeatureFlagsStore.subscribe()` attaches the `config/featureFlags` `onSnapshot` at app boot —
**before** Firebase Auth resolves. A Firestore listener that hits `permission-denied` is torn down
**permanently** (the store guards `if (_unsub) return`, so it never re-subscribes), which left flags
stuck on defaults for the whole session even after auth. The doc comment already said "Public
read-only", so the fix is `allow read: if true` (these are non-sensitive UX kill switches — no PII,
no money, no secrets; write stays `if false`). **Inert until `firebase deploy --only firestore:rules`.**

## 4 — Phone auth reCAPTCHA error (the deep one)

**Symptom:** on the physical dev device, phone sign-in throws
`[auth/unknown] The reCAPTCHA SDK is not linked to your app`.

**Root cause:** Firebase iOS phone auth uses **silent APNs push** for app verification, falling back
to **reCAPTCHA** when that push can't be delivered. APNs `.p8` keys *are* uploaded to Firebase (Dev
`M2F5339KYF` + Prod `BM42K87CP9`, team `4R55F73KCP`) and FCM tokens register fine — but the local
`pnpm build:local` is a **development-signed Debug build** whose `aps-environment` entitlement had
defaulted to **`production`**. A dev-signed build can only receive pushes on the **sandbox** gateway,
so Firebase Auth's silent push never landed → reCAPTCHA fallback → the (unlinked) `RecaptchaEnterprise`
SDK error. Only `RecaptchaInterop` is in the Podfile.lock; the Enterprise SDK is intentionally not
linked (the code author flagged the reCAPTCHA web flow as "brittle" and chose APNs + a disable flag).

**Fix:** `app.config.js:75` already had the lever —
`"aps-environment": process.env.EXPO_PUBLIC_APNS_ENV === "development" ? "development" : "production"`.
Set `EXPO_PUBLIC_APNS_ENV=development` in `.env` (documented in `.env.example`) and regenerate native
so the entitlement bakes in as `development` → dev build registers a **sandbox** APNs token → matches
the uploaded Development key → silent push lands → no reCAPTCHA.

**Dev vs prod (important — does NOT leak):**
- `pnpm build:local` = Debug, development-signed → sandbox → `aps-environment=development`. ✅ correct for the test phone.
- `eas build --profile production` = distribution-signed → production. EAS does **not** read the gitignored local `.env`, and its prebuild leaves `EXPO_PUBLIC_APNS_ENV` unset → defaults to `production`. ✅ App Store build is unaffected.

**Verify the entitlement after prebuild** (the shell `echo $EXPO_PUBLIC_APNS_ENV` is always blank —
Expo loads `.env` into the build process, not your shell):
```bash
grep -A1 aps-environment ios/Niyah/Niyah.entitlements   # dev build → <string>development</string>
```

**Contingency if reCAPTCHA persists after the sandbox rebuild:** Firebase **reCAPTCHA Enterprise**
enforcement (Authentication → Settings) can stick "on" and demand the SDK regardless of APNs
(firebase-ios-sdk#15345). Set it to not-enforced, or link the `RecaptchaEnterprise` pod by adding it
to `MODULAR_HEADER_PODS` in `plugins/withFirebaseStaticFrameworks.js`.

## 6 — Deposit > $500 fails server-side instead of being blocked in-app

**Symptom (device):** entered **$100,000** in Add Funds, tapped the button → `createPaymentIntent`

**Root cause:** the deposit screen had **no client-side max** (`isValidAmount = amountInCents >= 100`,
min only). The server caps a single deposit at `MAX_DEPOSIT_CENTS` (default **50000¢ = $500**;
`functions/src/index.ts:407`, enforced at `:1127`). Display also rendered the raw entry string

**Fix (Robinhood-style — block before submit; client-only, no deploy):**
- `src/constants/config.ts` — added `MAX_DEPOSIT_CENTS = 50000`, mirroring the server (comment notes
  it's per-transaction anti-fraud, **not** a balance/earnings cap).
- `app/session/deposit.tsx` — `isValidAmount` now also requires `amountInCents <= MAX_DEPOSIT_CENTS`;
  over-cap → button **greys out** + red note **"You can deposit up to $500 at a time."**; static hint
  **"Min $1 · max $500 per deposit"** under the balance (mirrors the withdraw screen's cap line);
  button label flips to **"Max $500 per deposit"**. Added a defense-in-depth guard in
  `handleStripeDeposit` (`> MAX_DEPOSIT_CENTS` → early return) so it can't reach Stripe even if the

- `src/utils/format.ts` — new `formatAmountInput()` gives live thousands-grouping + `$` prefix while

## 8 — Withdraw daily-$25k limit is a read-then-check race (TOCTOU) [medium — found in audit]

**What:** `requestWithdrawal` sums the user's prior-24h withdrawals and checks
`dailyTotal + amount > $25k` (`functions/src/index.ts:3596-3624`) **outside** the
`db.runTransaction()` that performs the debit (`:3681-3712`). That transaction re-reads `balance` but
**not** the daily aggregate, so two+ concurrent requests can all read the same pre-commit daily total,
all pass the cap, then all commit.

**Real but bounded — NOT a launch blocker, NOT a money-safety / de-pool bug:**
- Only the user's **own** withdrawable balance moves. The debit transaction is fully atomic (re-reads
  `balance`, throws on `current < amount`, draws buckets down together) → no overdraw, no ledger drift
  (`balance == Σbuckets` holds), no double-pay, no cross-user redistribution, no platform-fund leak.
  The audit's first-pass "leak $150k+ from the platform" framing is **false**.
- Blast radius is one **velocity throttle**, hard-bounded by the per-user rate limit (**3
  withdrawals/hr**, enforced atomically at `:1028` / `checkRateLimit`) and the **$10k/txn** cap
  (`:3582`). Realistic overshoot ≈ one extra ~$10k beyond the $25k/day policy, of the user's own money.
  (The first-pass "$15k + $12k" example is impossible — $10k/txn cap.)
- **Won't appear in the device smoke** (needs concurrent requests + a >$25k balance).

**Fix (shipped — Fardeen chose patch-now):** made the cap atomic via a **counter on the wallet doc**
(`dailyWithdrawalDate` / `dailyWithdrawalTotal`, UTC calendar-day), read + written **inside the same
`runTransaction` as the debit**. Two concurrent withdrawals contend on the wallet doc, so the second
re-reads the first's committed counter and is forced to honour the cap — race closed. Chose the
wallet-doc counter over a separate `withdrawalDaily/{uid}` doc because it needs **zero extra
reads/writes** (the debit txn already reads+writes the wallet) and the decrement piggybacks on the
existing balance-restore write, so increment and decrement are each **paired 1:1 with the balance
mutation** → the counter can never drift from real withdrawals.

- `functions/src/wallet.ts` — new pure helpers `computeDailyWithdrawalState()` + `utcDayKey()`
  (a prior-UTC-day or missing/negative counter is treated as 0, so the cap resets cleanly at UTC
  midnight and a rare cross-midnight decrement leftover can never wrongly block).
- `functions/src/index.ts` — `DAILY_WITHDRAWAL_CAP_CENTS` (env-tunable, $25k default); friendly
  pre-check after the wallet read; **authoritative** check inside the debit txn (throws `DAILY_LIMIT`
  → clean 400, no debit/no counter bump); `restoreWithdrawalReservation` now also
  `increment(-amount)` on the counter, atomic with the balance restore (covers all 6 abort paths).
  The `sent_with_warning` path (money already moved) correctly does **not** decrement.
- **Trap avoided:** a naive "move the collection query inside the txn" would *not* close it — Firestore
  won't conflict on a *new* sibling txn doc (phantom read); the shared wallet doc is what forces the
  serialization.
- **Semantics note:** the cap moved from a **rolling 24h window** → **UTC calendar day** (matches
  `DAILY_STAKE_CAP`). Required to enforce it atomically with one counter. No migration — existing
  wallets have no counter field; the first post-deploy withdrawal seeds it (treated as 0 for today).

**Verified:** client **cannot** tamper with the counter — `firestore.rules` `wallets/{uid}` is
`allow update, delete: if false` and `create` requires `balance == 0`. Reconcile compares
`balance` vs Σtransactions and **ignores** the two new metadata fields (no false-freeze). No
server path blanket-`set`s the wallet mid-day (only the merge path's fresh-create branch + a
`merge:true` on the defunct wallet — neither wipes a live counter). `/vibe-security` on the diff:
**no Critical/High/Medium/Low.** Tests: 8 new `computeDailyWithdrawalState` cases (incl. the
finding-#8 concurrency model + restore-frees-headroom). `pnpm run ci` green — eslint 0 · tsc 0 ·
jest · functions **60/60** (was 52).
